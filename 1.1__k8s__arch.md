## 🏗️ **Kubernetes Architecture — Deep Dive**

Kubernetes follows a **Master–Worker** architecture (or **Control Plane–Node** model).

At a high level:

* The **Control Plane (Master Node)** manages the cluster.
* The **Worker Nodes** actually **run your application containers**.

Let’s explore in more detail 👇

---

## 🧠 **1️⃣ Control Plane (Master Node Components)**

These components make global decisions about the cluster — scheduling, scaling, and state management.

---

### 🧩 **a) kube-apiserver**

* It is the **front door** of the Kubernetes control plane.
* Every interaction (CLI, UI, or automation) goes through this component.
* It exposes the **Kubernetes API** (RESTful API over HTTPS).

**Functions:**

* Validates and processes REST requests (like `kubectl apply`).
* Updates the cluster state in `etcd`.
* Authenticates and authorizes requests.
* Serves as the **communication hub** between all control plane and worker components.

📘 Example:
When you run:

```bash
kubectl create deployment nginx --image=nginx
```

→ `kubectl` sends a REST API request to `kube-apiserver`.
→ `apiserver` stores desired state in `etcd` and notifies the scheduler.

---

### 🧩 **b) etcd**

* A **key–value store** that acts as the **brain of Kubernetes**.
* Stores the **entire cluster state** (desired + current state).
* Highly available and distributed.

**Functions:**

* Keeps data on pods, deployments, configs, secrets, etc.
* Supports leader election and state recovery if the control plane fails.

🧠 Think of `etcd` like a **database for Kubernetes** — but optimized for speed, reliability, and consistency.

---

### 🧩 **c) kube-scheduler**

* Decides **which node** should run a new Pod.
* Doesn’t run the Pod itself — only assigns it.

**How scheduling works:**

1. A new Pod is created (by Deployment or ReplicaSet).
2. Scheduler checks all available nodes.
3. Evaluates filters (like CPU, memory, taints/tolerations, node affinity).
4. Assigns the Pod to the “best fit” node.

📘 Example:
If Node A has 80% CPU free and Node B has 30%, the scheduler likely picks Node A.

---

### 🧩 **d) kube-controller-manager**

* Runs **multiple controllers** — each responsible for maintaining a part of cluster state.
* It ensures the actual cluster state matches the **desired state** stored in `etcd`.

**Main controllers include:**

* **Node Controller** → Detects & replaces failed nodes.
* **ReplicaSet Controller** → Ensures correct number of Pod replicas.
* **Deployment Controller** → Manages rolling updates & rollbacks.
* **Job Controller** → Runs and tracks jobs.
* **Endpoint Controller** → Populates Services with Pod IPs.

📘 Example:
If a Pod dies unexpectedly, the **ReplicaSet controller** notices the difference and creates a replacement Pod.

---

### 🧩 **e) cloud-controller-manager** (Optional)

* Used in **cloud environments** (AWS, GCP, Azure).
* Integrates Kubernetes with cloud-specific APIs (load balancers, storage, instances).

**Example:**
When you create a Service of type `LoadBalancer`, this controller calls your cloud provider API to provision an actual load balancer.

---

## 🧠 **2️⃣ Worker Node Components**

Each worker node runs your **Pods (containers)** and reports back to the master.

---

### 🧩 **a) kubelet**

* **The heart of each node** — the "node agent."
* Talks directly with the `kube-apiserver`.
* Ensures that the **containers defined in the PodSpec are running**.

**Key functions:**

* Registers the node with the cluster.
* Watches for Pod specs assigned by the scheduler.
* Uses the container runtime (e.g., Docker, containerd, CRI-O) to start containers.
* Reports node and Pod status back to the API server.

📘 Example:
If a Pod crashes, kubelet automatically restarts it (based on policy).

---

### 🧩 **b) kube-proxy**

* Manages **network rules** on each node.
* Enables **service discovery and load balancing** within the cluster.

**Functions:**

* Maintains IP tables or IPVS rules to route traffic to Pod IPs.
* Ensures that when you access a **Service**, requests go to the correct backend Pods (round-robin).

📘 Example:
When you access `ClusterIP:80`, kube-proxy forwards it to one of the Pod IPs behind that service.

---

### 🧩 **c) Container Runtime**

* The **actual engine that runs containers**.
* Kubernetes supports multiple container runtimes:

  * **containerd**
  * **CRI-O**
  * (Old) Docker — replaced internally by containerd via CRI (Container Runtime Interface).

**Functions:**

* Pulls images from container registries.
* Starts and stops containers.
* Manages container lifecycle (logs, networking, etc.)

📘 Example:
When kubelet tells “run Pod X using nginx:latest”, the container runtime:

1. Pulls `nginx:latest` from Docker Hub.
2. Starts the container inside the Pod.
3. Connects it to the Pod network.

---

### 🧩 **d) Pods**

* The **smallest deployable unit** in Kubernetes.
* A Pod wraps one or more containers that share:

  * **Network namespace** (same IP/port space)
  * **Storage volumes**
  * **Lifecycle**

📘 Example:
A single Pod can run:

* Your app container
* A sidecar container (like a log forwarder or metrics collector)

---

## 🔄 Control Plane–Node Communication Flow

```text
kubectl → kube-apiserver → etcd (stores desired state)
                ↓
         kube-scheduler (assigns Pod to node)
                ↓
             kubelet (on node)
                ↓
     container runtime (runs containers)
                ↓
          kube-proxy (handles networking)
```
